# Port 292: HordeContain investigation

## Carry-over template

The HordeContain create path RW 0x64B5D5 reaches constructor RW 0x8727F9, which installs the HordeContainInterface table RW 0xC5B1F8 at object +0x11C (RW 0x872873). Table slot +0x274 is RW 0x86D6FD: it copies the AsciiString at module-data +0x280, not a Boolean or a template pointer. The field row is RW 0xC5BDF0, parsed by RW 0x42EE5E; its name is LivingWorldOverloadTemplate. The cavalry constructor installs table RW 0xC5BE98 at the same interface offset (RW 0x8798A1), and its corresponding slot also points to RW 0x86D6FD.

Object's carry-over record builder RW 0x6917BB checks HERO first (RW 0x6917DF), then HORDE (RW 0x69184B). For a non-hero horde it obtains the interface RW 0x68C866, calls slot +0x274 at RW 0x691869 and tests the returned string for non-emptiness through RW 0x401E64. If present it calls the same slot again and copies the string to the record at RW 0x6918A5..0x6918B6. If absent, or if there is no interface, the template's own name is used at RW 0x6918C7..0x6918DE. Hero handling remains the preceding branch, not a second horde path. The caller for campaign victory is RW 0x5EBAEE; the existing port is `CampaignCarryover::recordOf` and `onCurrentMissionWon`.

The older field triage incorrectly attributes RW 0x881A5E to HordeContain: the reader is in the RiderChangeContain path, not a read of the horde field. Its factory RW 0x64BA11 calls constructor RW 0x881501 (RW 0x64BA3B); that installs its contain table RW 0xC5DFA8 at +0x20 (RW 0x88153F), whose slot +0x5C contains RW 0x881A5E. Thus the +0x280 byte at RW 0x881A95 belongs to RiderChangeContain's data, not HordeContainModuleData. The record builder above has an independent, complete interface-to-vtable chain and proves a real read of the horde field. BFME2 donor search for the field name in Code yielded no named counterpart; the evidence here is RotWK disassembly, not donor inference.

The other confirmed reader of slot +0x274 is AIWoTRForfeitTactic update RW 0x9B7458: at RW 0x9B770E / 0x9B7732 it retrieves the overload name and compares it against RW 0xC89C78. A match skips owned upgrade cost (RW 0x9B7782); a nonmatch or empty name includes it. `AITacticalAI.cpp::forfeitScore` instead uses the object's name, explicitly marked INFERENCE in S-7187. That scorer is owned by open Port 33 (fork issue 105), so it is not changed here; see S-7518.

A supplementary byte-seeded Capstone scan over every executable PE section looks for memory `call`/`jmp` operands with displacement +0x274: exactly four candidate instructions, RW 0x691869 / 0x6918A5 and RW 0x9B770E / 0x9B7732, all in those two readers. A further `.text` candidate scan found no `mov reg,[...+0x274]` followed by a call/jump through the same register within eight instructions before a clobber, branch or call. Scanning +0x280 memory-displacement candidates in the horde address region also finds RW 0x87293C and RW 0x87848B on the **module instance** (the latter is its xfer), RW 0x878D3B (data destructor), RW 0x8790D7 (data constructor), and RW 0x881A95 / 0x881D96 on RiderChangeContain; a spurious overlapping decode at 0x86D70D starts inside the actual `add eax, 0x280` of RW 0x86D6FD. These byte-seeded scans are candidate inventories, not proof against inlining, pointer arithmetic, more distant register-loaded vslots, or disassembly overlap: additional data-flow attribution outside this region is still required before claiming every reader. The scanned retail bytes remain uncommitted.

## Ennorath definitions and game-check target

The 1.9.8.3 INI archive has 24 explicit `LivingWorldOverloadTemplate` assignments in HordeContain / HorseHordeContain blocks (21 / 3; ChildObject blocks counted separately), not 24 proven active campaign records. Examples are `AngmarOrcWarriors` and `AngmarWolfRiders` -> `AngmarThrallMaster`, `AngmarNecromancerHorde` -> `AngmarNecromancer`, `RhudaurBarbarianAxeHorde` and `RhudaurWolfRiderHorde` -> `RhudaurWarlord`, and the three `Isengard*HordeForHauptmannSummon` -> `IsengardUrukHauptmannForSummon`. Inherited and overridden objects require the effective INI loader, and a definition only affects this path if its object is non-HERO HORDE and is actually marked for campaign carry-over.

Owner game check, **not yet performed**: in an appropriate campaign scenario arrange a qualifying horde with a nonempty overload, win and inspect its carry-over into the next mission against RotWK; include a no-overload horde as a control. The soldier formation/front-rank check requested by the issue is a separate neighbouring behaviour: this patch does not change it, and PORT-81 established that `RanksToJustFreeWhenAttacking` has no behavioural reader. No visible movement or front-rank change is claimed here.

`RanksToJustFreeWhenAttacking` already has a detailed proof and regression tests in `docs/ennorath/PORT81_RW_ANALYSIS.md`, `docs/STOPS.md` S-7213 and `engine/tests/test_port_81.cpp`: parser row RW 0xC5BB90, data offset +0x1C4, constructor/copy sites RW 0x878F5D, 0x878C91, 0x878D97, and the established whole-text displacement scan found no behaviour reader. Its neighbour `RanksToReleaseWhenAttacking` at +0x1B8 is read by RW 0x875221, RW 0x87545C and RW 0x875562. Do not invent a second release path from the field name.

## Further work

The other uncited functions still require classification against their callers and the other open ownership boundaries. In particular RW 0x870D4E iterates the contained list and the entering-member map, optionally filters each object, skips missing drawables, and invokes Drawable RW 0x672B96 then RW 0x67093E. A byte-seeded search for indirect `call`/`jmp` with displacement +0x1F0 in all executable sections yielded only four candidates. RW 0x48EAA3 is **not** a horde call: its function RW 0x48EA29 invokes slots on `esi` in a loop over global UI state and belongs to W3DInGameUI. RW 0x59B124 acts on refcounted elements of another collection; RW 0x743B6D belongs to AI guard state's on-exit RW 0x743B40 (`AITNGuard.cpp`) and calls the owner's AI at Object +0x260 with no four decal arguments; RW 0x83B148 acts on the global camera interface. A supplementary `.text` candidate scan found no `mov reg,[...+0x1F0]` followed by a call/jump through the same register within eight instructions before a clobber, branch or call; a byte scan found no relative direct `call`/`jmp` to RW 0x870D4E either. These results are not proof that the decal has no caller: another vtable displacement, an indirect call through a function pointer, or a more distant register-loaded slot can evade these searches. Its caller and client event path still need proof; do not introduce a simulation-to-drawable direct call (the existing thread boundary is `ObjectClientHooks`).

## Map horde upgrades and the member-only query

Map property application calls RW 0x693A9A for `objectUpgradesList`. On each known upgrade, its HORDE branch obtains the horde interface at RW 0x693AEB; if that exists, it asks slot +0xB4 RW 0x86BDC0 at RW 0x693AFB and calls slot +0xB8 RW 0x871A90 at RW 0x693B0C only when the answer is false. The +0xB4 wrapper reads the upgrade's +0x38 bit and preserves the Boolean result of slot +0xB0 RW 0x86EC2D: **any contained member or resolved entering member** has that bit. It is not a query of the horde object's own mask. The +0xB8 body gives the upgrade to the horde, then to contained members (all of them for the true flag), then unconditionally to entering members and flashes the affected drawables (RW 0x871B30..0x871B7C); retail's entering-loop lookup is not null-guarded, so do not silently assert a null policy.

`Object::hasUpgrade` implements the contained-member part but also checks the owner's mask, and S-486 still records the missing entering IDs. `HordeContain::giveUpgrade` handles the horde and contained members but omits the entering loop and flash; `MapObjectLoop::create` deliberately reports the whole HORDE map-list path unported and incorrectly references the already-closed S-483. Thus simply substituting `hasUpgrade` or merely wiring `giveUpgrade` would not reproduce the full path. This crosses the shared member upgrade / garrison path S-7505 / S-486 and map lifecycle: #552 has the facts for coordination. A follow-up should test no interface, owner-only upgrade, an upgraded contained member, an upgraded entering member, all-members delivery and entering-member flash; retain the order and check side effects before changing it.

## Flank reset and attack-machine ownership

RW 0x87159F is not a mere generic tree clear: its vtable slot +0x250 restores the flank eligibility byte and clears the flank expiry map. Two proven callers are destructors RW 0x7414CD and RW 0x741564: each checks its owner at +0x14, obtains the horde interface through RW 0x68C866, and calls slot +0x250 at RW 0x7414FC and RW 0x741593 respectively. Their vtables RW 0xC28178 and RW 0xC28350 are installed by attack-machine constructors RW 0x744D73 and RW 0x74548D respectively; the former is the HordeAIUpdate attack machine, the latter the horde attack-position machine (`HordeAIUpdateCombat.cpp`, `AIAttackHordePosition.cpp`). The BFME2 donor `HordeContainIface11CSlots.cpp::rva0046E2BC` agrees on the clear, but RW is the authority.

The port carries `m_flankers` and `m_canFlank` in both crc and xfer but never resets either after creation. The assertion in `HordeFlank.cpp` and S-582 that retail never clears them is therefore incorrect. A reset without its exact machine destruction lifecycle is not equivalent; changing the HordeAIUpdate lifecycle is outside this issue (open #650), and the second caller shares AI state machinery. This is a separate omission from S-7519's factory hand-off; all three reserved fragment ids S-7518..S-7520 are already occupied, so it needs its own newly reserved stop rather than silently conflating the mechanisms. Follow-up needs the matching destruction/ownership sequencing and a regression that verifies a previously flanked attacker becomes eligible and the expiry map is emptied only on the corresponding machine destruction; also correct S-582 and its port comment as part of that fix.

- **Поля:** `FIELD_GAPS.tsv` помечает `HordeContain.RanksToJustFreeWhenAttacking` (82 определения) и `HordeContain.LivingWorldOverloadTemplate` (21) как `parsed-unused`.
